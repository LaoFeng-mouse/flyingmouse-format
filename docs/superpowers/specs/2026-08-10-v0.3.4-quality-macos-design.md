# Mahiro Format v0.3.4 Quality and macOS Design

## Objective

v0.3.4 turns the existing v0.3.3 format coverage into a more dependable product. It fixes durable conversion preferences, isolates LibreOffice user profiles on clean Windows installations and Microsoft Store packages, closes the conversion-quality defects found during the v0.3.3 audit, and adds unsigned GitHub-first macOS builds for Apple Silicon and Intel without changing the mouse UI.

The release remains blocked until Windows 10/11, Windows 7 staging, macOS arm64, and macOS x64 gates pass. Automated macOS jobs are not presented as physical-device acceptance, and macOS Audio Vivid AV3A NCM remains unsupported because the bundled AVS3 decoder is Windows-only.

## Confirmed Windows 11 LibreOffice failure

The affected computer runs Windows 11, so LibreOffice 26.2 operating-system compatibility is not the primary cause. v0.3.3 calls `soffice --version` without a writable `UserInstallation` before it creates the isolated profile used by the real conversion. On a clean or packaged installation this bare probe can fail while creating the default LibreOffice user installation and display the reported fatal dialog.

All LibreOffice operations in v0.3.4 use the same headless runner:

- create a unique writable profile below `FLYINGMOUSE_RUNTIME_DIR` before starting LibreOffice;
- pass `-env:UserInstallation=<file URL>` to capability probes and conversions;
- suppress GUI interaction and enforce a short probe timeout;
- capture exit code, signal, stdout, and stderr into the application log;
- expose stable bilingual engine error codes instead of only `失败 1 个`;
- remove the isolated profile in `finally` without touching a user's system LibreOffice profile.

Win7 keeps a separately pinned LibreOffice resource that must be exercised from the isolated Win7 staging tree. Win10/11 and macOS use their own locked engine manifests. A successful probe means the packaged executable actually ran with a writable profile; file existence alone is insufficient.

## Durable settings

`settings.json` becomes a versioned settings document owned by the Electron main process:

```json
{
  "schemaVersion": 2,
  "lastSaveDirectory": "C:\\Users\\example\\Desktop",
  "targetBySource": {
    "pdf": "xlsx",
    "ncm": "mp3"
  },
  "language": "zh-CN"
}
```

The renderer accesses settings only through trusted IPC. Target extensions and values are normalized and validated before an atomic replace. A user change updates every selected source extension, matching v0.3.3 batch semantics. A mixed selection restores a target only when every source extension remembers the same target and that target remains available.

On first v0.3.4 launch the renderer may submit the legacy value from `flyingmouse.conversionPreferences.v1` and `flyingmouse.language.v1`. The main process merges only missing keys, then the renderer deletes the migrated origin-local keys. The migration is best effort because old values are partitioned by v0.3.3's random localhost ports. Save-directory behavior remains unchanged: update only after a successful save and fall back to the Downloads folder if the remembered directory no longer exists.

## Diagnostics

The Help/diagnostics action exports a UTF-8 text report chosen through an Electron save dialog. It includes app version, OS release and architecture, package type, engine paths reduced to safe basenames, engine versions, probe results, error codes, and a bounded tail of `debug.log`. It excludes source file paths, source filenames, converted content, credentials, environment-variable values, and unrestricted logs.

Engine failures use stable codes including:

- `OFFICE_ENGINE_MISSING`
- `OFFICE_ENGINE_INCOMPATIBLE`
- `OFFICE_ENGINE_PROFILE_FAILED`
- `OFFICE_ENGINE_START_FAILED`
- `OFFICE_CONVERSION_FAILED`

The API keeps the existing `error` field and adds `errorCode` plus `messages.zh-CN` and `messages.en-US`. The renderer selects the message for the active language and shows the code beside the failed batch item.

## Conversion-quality repairs

The v0.3.3 audit findings become explicit regressions:

- Presentation HTML export must contain slide text and must reject an empty-body export.
- Markdown to HTML must preserve headings, emphasis, strong text, links, ordered and unordered lists, and fenced code blocks.
- HTML and DOCX to Markdown must preserve simple tables as Markdown tables; complex spans fall back to safe HTML instead of flattening content.
- Animated GIF input must never become a vertical sprite. Static targets use the first composited frame and report that animation was flattened; animated WebP/TIFF paths must preserve frame count and timing or be removed from the advertised matrix.
- Alpha-capable output preserves transparency. Opaque JPG output composites onto an explicit user-visible default background instead of silently producing black.
- Nested JSON to CSV uses deterministic dot notation for objects and JSON strings for arrays; it never emits `[object Object]`.
- XLSX to CSV identifies the exported sheet and warns when other sheets or formula expressions are not preserved.
- NCM output re-applies available title, artist, album, and cover metadata after transcoding. Standard NCM is supported on macOS; AV3A NCM is declared Windows-only.
- Complex PDF table extraction is re-evaluated against the supplied scanned sample with cell-position scoring, table-count checks, sheet-name checks, merge checks, confidence notes, and Raw fallbacks. Generating an XLSX file alone is not success.
- WPS/WPT/WPD, ET/ETT, DPS/DPT, HEIC, and KGG remain unverified until real fixtures exist and are not described as fully validated.

## Platform engine layout

Engine lookup becomes platform-aware while keeping the current environment overrides for tests:

| Platform | FFmpeg | LibreOffice | Poppler | AVS3 |
| --- | --- | --- | --- | --- |
| Win10/11 x64 | `ffmpeg.exe` | locked 26.2 resource | `pdftoppm.exe` | bundled Windows decoder |
| Win7 SP1 x64 | staging-pinned Windows build | separately pinned Win7-compatible resource | staging-pinned build | bundled Windows decoder |
| macOS arm64 | native arm64 binary | native Apple Silicon app binary | native arm64 binary | unavailable |
| macOS x64 | native x64 binary | native Intel app binary | native x64 binary | unavailable |

macOS uses `process.platform` and `process.arch` to select resources. The minimum declared macOS version is 11. Native modules are installed and packaged for the target architecture; a build does not borrow modules from another runner or architecture.

## macOS packaging and publication

GitHub Actions builds and tests two unsigned DMGs:

- `Mahiro Format-Setup-0.3.4-mac-arm64.dmg`
- `Mahiro Format-Setup-0.3.4-mac-x64.dmg`

The workflow runs on native arm64 and Intel GitHub-hosted macOS runners, restores SHA-256-pinned engine assets for that architecture, runs engine probes and representative real conversions, inspects the app bundle and native Mach-O architectures, and uploads artifacts only after validation. No signing secrets or placeholders are added. The GitHub release and README clearly state that these first DMGs are unsigned and not notarized, may trigger Gatekeeper, and still require physical Mac acceptance.

The Microsoft Store remains Windows-only. Mac App Store work is deferred until an Apple Developer Program account, Developer ID/App Store certificates, notarization credentials, sandbox entitlements, and physical Mac acceptance are available.

## Tests and release gates

Each change follows RED/GREEN tests. Required gates are:

1. engine-free unit/security/UI tests on Windows;
2. real Windows conversion suite with locked engines and supplied fixtures;
3. standard NSIS and APPX build, unpacked-app smoke, app-package content, icon, and engine-profile probe;
4. isolated Node 22 Win7 staging tests, Electron runtime probe, Win7-compatible LibreOffice conversion, PE 5.2, ASAR/resources/icon, and installer smoke;
5. native macOS arm64 and x64 tests, real engine conversions, bundle architecture checks, and app launch smoke;
6. production dependency audits for root and Win7 staging;
7. real NCM and AV3A fixtures on Windows, and standard NCM only on macOS;
8. artifact filenames, byte sizes, SHA-256 values, and download URLs read back from GitHub.

Failure of any required gate prevents the `v0.3.4` tag and release. Windows 7 and both macOS architectures remain explicitly marked as awaiting physical-device acceptance when such devices were not used.

## Repository and delivery safety

Implementation starts from clean GitHub `main` commit `b536c8d` in an isolated `v0.3.4-quality-macos` branch. The retained v0.3.3 installation and installers under `D:\34615\Mahiro Format 0.3.3` are read-only evidence and are not modified. Generated engines, credentials, certificates, build output, and user diagnostics are never committed.

The release updates `main` and creates `v0.3.4` only after all gates pass. It does not overwrite v0.3.3 assets or change the existing Microsoft Store submission during the GitHub-first macOS phase.
