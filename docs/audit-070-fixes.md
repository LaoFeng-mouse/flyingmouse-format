## 核心转换

### Markdown → Word、HTML、PDF

`text-docx.js` 的 Markdown → DOCX 入口已接入独立实现的 `markdown-document.js`，使用随包提供的 Pandoc 3.11 解析文档树，再生成 DOCX。正文不再按行用正则删除 Markdown 符号。标题、表格、嵌套列表、引文、代码、超链接和数学在各自节点内处理；代码块中的 `**literal**`、`==literal==`、`$  X  $` 和 `<u>literal</u>` 保持字面值。

真实输出检查确认 Heading1 样式、Word 表格、嵌套编号、超链接关系、下划线、黄色高亮和三个可编辑 OMML 公式；分式与根号生成对应的数学结构。Markdown → PDF 使用同一个 DOCX 中间产物，再由 LibreOffice 渲染。本轮已实际转换并查看 PDF 页面，确认中文、表格、代码、行内公式、分式、根号、下划线和高亮可见。

Markdown → HTML 使用独立的 Marked 数学扩展和 KaTeX 0.18.7，输出离线 MathML；不需要运行文档脚本或访问 CDN。代码节点不经过公式规范化。未知公式宏会返回 `MARKDOWN_MATH_UNSUPPORTED`，不会把未渲染公式当成成功转换。

图片必须随源文档提供并位于其资源目录内，或使用支持的内嵌图片。DOCX 转换会复制允许的本地图片到本次独立临时目录；缺图、越界路径和远程图片保留说明文字，并通过 API 返回 `MARKDOWN_IMAGE_UNAVAILABLE`。不会偷偷读取任意本地文件或联网补图。浏览器上传单个 MD 通常不包含其旁边的图片目录，因此外链图片仍需用户一并提供或内嵌，这属于输入资源边界。

`getTools()` 实际运行 Pandoc `--version`，将能力和诊断传给前端。没有可运行 Pandoc 时，MD/markdown 不提供 DOCX、PDF 目标；界面明确提示修复安装。TXT/HTML 的既有简易 DOCX 路线以及 MD → HTML 不依赖 Pandoc。所有 `MARKDOWN_*` 内容转换错误以 HTTP 422 和稳定错误码返回。

仍不承诺支持全部 LaTeX 宏包、Mermaid、任意原始 HTML、网页 CSS 或网络资源。Pandoc 对不支持内容的诊断会成为结果 warning；原始 HTML/TeX 中不能可靠转换的部分按原文保留并提示，不执行文档提供的模板、脚本或外部资源。DOCX 结构和 LibreOffice 渲染已验收；Microsoft Word/WPS 原生打开和每一种字体环境仍需分别检查。

### PDF → Word 和混合 PDF

本批修复涉及 `pdf-table.js` 的坐标、文字行重建，以及 `pdf.js` 的正文顺序、内容校验和逐页 OCR。实际反例复测结果：

- 90° 页面旋转、逐字绘制的 `HORIZONTALTEXT` 现在按显示坐标重建成完整一行，不再生成 14 个倒序单字段落。
- 一行 8 个独立定位单词不再被误判成 8 列表格；标题、正文、结语保持源文件顺序。真正的多行简单表格继续生成可编辑表格。
- 真实 docengine 在旋转样本上遗漏 I/L 的输出被文字覆盖检查拦截，随后重建成完整 `HORIZONTALTEXT` 并返回版式降级 warning。普通正文样本仍走真实 docengine 快速路径，不无故降级。
- 混合 PDF → DOCX 的真实结构引擎测试耗时约 31.2–81 秒；原先遗漏的标题补回可编辑文本，扫描页 `SCAN_BODY_42` 保留。混合 PDF → TXT/HTML 逐页判断并 OCR，扫描正文不再整页消失；实际识别成 `SCAN BODY 42`，下划线变为空格，所以没有宣称 OCR 标点完全保真。

这些判断来自真实输出的文字、结构和页面检查。六个 DOCX 经真实 LibreOffice 转 PDF，共九页全部查看：旋转样本呈现完整一行，普通原生路线保留标题字号/文字间距，3×3 表格对照保留可编辑表格、标题、结尾和图片且不降级。混合样本输出四页，前两页为可编辑重建、后两页为原件对照，未看到截断或乱码。不能只检查 DOCX 是 ZIP 或 HTTP 返回 200。

PDF 源文档通常不包含可直接复用的 Word 段落和表格语义。即使文字覆盖检查通过，也不等于复杂分栏、竖排、合并表格、数学、扫描图片和原稿版面百分之百还原；本次修复不能升级成这种产品承诺。结构引擎较慢的样本需要等待，仍可能出现 OCR 字符或标点差异。

## PasteMD 的借鉴范围

上一轮对照的 [PasteMD 提交 5dce748a…](https://github.com/RICHQAQ/PasteMD/tree/5dce748a81b1d384a8a10d900a6785698c1fb9ad) 使用 Pandoc、参考模板和后处理完成 Word 结构转换，这比逐行删符号更适合 Markdown。[Pandoc 官方数学说明](https://pandoc.org/MANUAL.html#math)明确了 DOCX 数学采用 OMML 的路线。

本项目独立集成 Pandoc 文档树，未复制 PasteMD 的 AGPL 实现。上一轮调用 PasteMD 实际默认 LaTeX 预处理函数，发现代码块中的 `$  X  $` 会被改写；本批通过按节点转换避免同类问题。没有运行 PasteMD 全部 Word/WPS 粘贴、模板和平台自动化，因此不宣称完整 PasteMD 已验收。其 [AGPL-3.0 许可证](https://github.com/RICHQAQ/PasteMD/blob/5dce748a81b1d384a8a10d900a6785698c1fb9ad/LICENSE)以及 Pandoc 自身许可都应按各自范围处理，不能把第三方引擎套用本项目的非商业声明。

## UI、插件与角色图

浅色、深色、随系统使用页面级主题选择，并持久保存；显式选择不被系统变化覆盖，跟随系统时响应运行中的配色变化。文档、PDF 和图片本身保持原颜色，主题改变应用界面。真实 Chromium 页面 18/18 检查通过，包括持久化、失败重试、晚到响应、转换预览、390/780 像素宽度，以及 Pandoc 缺失时中英文提示；12/12 核心文字背景颜色对达到 4.5:1。系统配色变化通过浏览器媒体模拟检查，未冒充真实 Store 安装后原生系统切换验收。

本机最新已核验的 Fantasy Mouse UI 包是 `0.2.0+codex.20260910074027`。插件不是应用运行时组件，更新插件不会自动改写本项目源码或 PNG。当前最需要修订的是参考选择规则：带已知手部冲突的完整工坊场景不应继续作为默认正向参考。

用户指出的拉杆场景确实违反角色规则：胸前 V/U 代表合拢的双手；角色进入操作姿态时，应删除胸前 V/U，并且只保留一对实际操作手。它不是乳头、肚脐或固定身体装饰。本项目后续 UI 工作应以这一语义、实际接触关系和最终尺寸检查动作素材，不能以资源哈希校验替代造型验收，也不能把固定工坊图反复当作不同产品首页。

本批主题沿用现有鼠鼠品牌状态图；应用已有角色是合手静态图，与用户否定的错误拉杆场景不同，没有为解决参考问题而误删正确合手素材。没有声称已重新绘制角色或完成全局插件更新。错误操作场景不应作为新增素材引入。全新动作素材、全局插件参考清单修正和用户对角色的视觉确认仍需作为独立结果记录。
